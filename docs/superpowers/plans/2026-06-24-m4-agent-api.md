# M4 — Agent / Admin API (MCP parity) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Build the **privileged agent/admin HTTP surface** (`/api/agent/*` + a public bean search) so the MCP server reaches full parity with its 11 tools through the backend — agent-attributed recipe creation, status/lineage transitions, any-status reads, agent-sourced feedback, and the preference read its context builder needs — all behind an agent-token gate.

**Architecture:** Same layering as M3 (`routes → services → repositories(packages/db) → db`). A new `agentAuth` middleware gates `/api/agent/*` on a bearer token. Agent recipe creation sets the txn-local `bd.owner_write_ok` flag so `bd_guard_recipe_owner_immutable` permits `created_by='agent'` (the trusted-writer path that replaces the old service-role). Context-summary assembly stays in `apps/mcp/src/context.ts` (repointed in M5) — M4 supplies the raw data endpoints it consumes.

**Tech Stack:** Node 22 (ESM, NodeNext), TS, Hono, Kysely + pg, Vitest, local Homebrew PostgreSQL 17 (no Docker). Builds on M2 (`@brewdial/db`) + M3 (client API) now in `main`.

## Global Constraints

- **Agent-token auth:** `/api/agent/*` requires `Authorization: Bearer <AGENT_TOKEN>` (from env / OCI secret; never committed/logged/`VITE_`). Missing/wrong → `401`. The token is a single shared service credential (M4 scope); per-agent tokens are future work.
- **Agent attribution is server-set:** agent recipe creation sets `created_by='agent'`, `owner_id=NULL`, `version=1`, `status='active'` server-side, wrapping the insert in a transaction that does `select set_config('bd.owner_write_ok','on', true)` so the `bd_guard_recipe_owner_immutable` trigger permits `created_by='agent'`. The client never supplies `created_by`/`owner_id`/`is_official`.
- **Agent feedback sources:** `/api/agent/feedback` allows `source ∈ {agent, mcp, coffee_profile, api}` (default `agent`) — complementing M3's public endpoint which restricts to `{web, coffee_profile}`. `recipe_code` comes from the body; verify the recipe exists (404 if not).
- **Any-status reads:** agent recipe reads return rows of ANY status (incl. `test`/`superseded`), unlike the public reads.
- **Response shape parity:** agent recipe/feedback responses project the same `RECIPE_COLUMNS`/`FEEDBACK_COLUMNS` the client mappers + MCP mapper consume (reuse the M3 repos' `RecipeRow`/`FeedbackRow` + projections). Reference `apps/mcp/src/mappers.ts` + `apps/miniapp/src/lib/data/mappers.ts`.
- **MCP behavior parity:** match the existing MCP tools' semantics — read `apps/mcp/src/repositories/recipes.ts` (create/update/setStatus/supersede), `beans.ts` (findBeans ILIKE), `tools.ts` for exact field handling (version bump on update, supersede sets old.status='superseded'+superseded_by, new.supersedes).
- Node>=22 ESM NodeNext; **apps/api MUST compile with tsc** (run `pnpm --filter @brewdial/api build` — vitest doesn't type-check); avoid TS2589 via explicit return-type interfaces; DB tests share `brewdial_test`, `fileParallelism:false`, re-run-safe seeds.
- **No new DB stored functions** beyond the owner-write-flag txn pattern (TS services + the existing `set_config` flag the guard already reads).

## Self-Review notes
- M4 = backend agent surface only. M5 repoints the MCP server (`apps/mcp`) to these endpoints (swap its PostgREST/service-role client for the agent-token HTTP client) and keeps `context.ts` building summaries from the new data reads. M6 = data import + cutover.
- The only privileged-write that needs the `bd.owner_write_ok` flag is agent recipe CREATE (for `created_by='agent'`); update/status/supersede touch status/lineage only and must NOT write owner/official/created_by (the guard raises on those UPDATE columns).
- Agent token is a single shared credential in M4; OCI-stored (M1 runbook). Per-agent tokens / scoped capabilities are future work.
- is_official setting (`rpc_set_recipe_official`) is NOT in the 11 MCP tools → out of M4 scope; the guard + flag pattern is in place to add it later if needed.
